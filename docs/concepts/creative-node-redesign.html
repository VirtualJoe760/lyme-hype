Creative nodes — panel redesign

Every creative node rebuilt as a workbench rather than a form. Dark Lime Cut, matched to theme.css. Lime stays rationed: active tool, active setting, Generate, live dot.

00. The philosophy

These came out of redesigning the image panel, but none of them are about images. They are the rules every creative node follows — §05 applies them to the rest.

The artifact is the subjectThe thing you're making sits at the top at full size. The panel is a workbench, not a form that happens to output something.
Tools act on the artifactThe toolbar edits what's in the preview. Dark until something exists to edit.
The tool picks the capabilityWhich tool is lit decides which models can run — so the model row rebuilds when the tool changes.
Models are pills, not a hierarchyYou pick "midjourney", never "muapi". Unreachable models stay visible and dim rather than hidden.
One text areaIts meaning changes with the tool; a second box would mean the panel doesn't know what it's asking for.
Settings are squares that show their valueThe panel answers "what will this do" without opening anything.
The primary button is a verbIt states the tool and the count. It refuses when the route can't run, instead of failing after the click.
Finish commitsGenerating is cheap and reversible; committing to the canvas is the deliberate act.
Never lieNo control that does nothing, no button enabled over a broken route, no silent reroute. Every claim on screen is true or absent.
No pricesThey go stale, they nag, and they're not the decision being made here.

04. Picking a tool re-frames the model row

The tool decides the capability; the capability decides the pills. Generating in Midjourney and then reaching for Inpaint is the case that proves it — Midjourney cannot inpaint at all, so the row has to rebuild and the panel has to say so rather than quietly rerouting your edit to another model.

  • RULE The row never shows a model that can't run the selected tool. Filtering happens on capability, not on connector.
  • RULE If the current model survives the tool change, nothing moves — picking Inpaint while on gpt-image-2 keeps gpt-image-2, no notice, no flicker.
  • RULE If it doesn't survive, the panel replaces it and says which model it left. Silent rerouting is the bug this whole redesign exists to kill.
  • EDGE With only muapi connected, Inpaint has zero available models. The row is empty and the button must refuse — this is the state most likely to be missed in build.
  • STYLE A real consequence worth naming: your edit runs on a different model than your generation, so it can drift in look. fal-ai/flux-krea-lora/inpainting accepts loras, so a trained style at least carries across — which is a reason to prefer it as the inpaint default.

DEEPFAKE — the chain is the toolbar, left to right

  • PROOF The audio node is the strongest evidence the philosophy generalizes. Today it has a four-way job switcher — voice / music / sfx / clone. Those aren't settings, they're tools: each maps to its own capability (audio-tts, audio-music, audio-sfx, voice-clone) and each reframes the model row exactly like Inpaint does. The pattern wasn't imposed on it — it was already there wearing tabs.
  • SHIFT LoRA breaks the "preview holds the output" reading, usefully. The artifact under construction is the training set, so that's what the preview holds — and Finish saves a reusable person rather than dropping a node on the canvas. The shape survives; what it commits to changes per node.
  • SHIFT Deepfake's toolbar is a sequence, not a set. Speech → Lipsync → Face swap runs left to right, with the preview carrying stage state (speech ✓ → face). Same row, read as a chain.
  • THIN Video's Extend button is thinner than it looks: only 4 models do video-extension, and Gemini's Veo caps at +7s × 20 requests, 720p. Face swap is thinner still — one model, muapi. Both need the same refuse-when-empty state as Inpaint.
  • LOCAL Audio's Isolate and video's Reframe are local ffmpeg — no model, no pill row, no network. Worth styling differently so it's obvious which tools are free.

An image is rarely the end of the thought — it's the start frame of a clip, a face to swap, a training image. Switching to Inpaint is not this: that's a tool inside the image node and the toolbar already covers it. These are the moves that change which node you're in, and the artifact travels with you as a named input.

  • One row, only once an artifact exists — same rule as the toolbar. Reuses the pill language rather than introducing a fifth kind of control.
  • Each pill names the node and the role the artifact will fill, because "send to video" is ambiguous — start frame and animate are different generations with different models.

  • Handing off commits. The artifact has to exist somewhere to be an input, so continuing implies the Finish step — which quietly answers the "what if I never press Finish" hole from §02.
  • REGISTRY ARTIFACT_HANDOFFS in model-catalog.ts — 12 routes across image/video/audio. The registry now drives three things: which models per tool, which nodes accept an artifact, and which tiles are ready at all.

07. Inpainting takes the canvas

A 330px panel is a bad place to brush a mask. It doesn't have to be — the app already does exactly this for Play view: playNodeId is set, PlayView replaces the middle area, the sessions rail hides, and playFrom remembers where to go back to. Inpainting reuses that takeover verbatim: the artifact gets the canvas, the panel keeps the controls.

  • Why this is the right split: the mask is part of the artifact, so it belongs on the artifact's surface. The prompt, model and action are panel controls and stay put. Nothing new is invented — the panel rows are the same rows.
  • It fixes the preview tension. The panel preview stops needing to be a work surface and becomes what it always was: a monitor. That's why it can stay small.
  • The takeover already has an owner in the code. playNodeId/ playFrom in store.ts, with App.tsx swapping the middle pane and hiding the rail. An editNodeId alongside it is a small, proven addition rather than a new layout mode — which is the difference between this being a week and being an afternoon.
  • OPEN Does the same takeover serve Expand (drag the canvas edges outward) and Reframe (crop handles)? Both are direct manipulation of the image at size, so probably yes — which would make this one editor surface with three modes, not three surfaces.
